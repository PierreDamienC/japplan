# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Japplan is a personal Android app (React + Capacitor) for tracking trips: an interactive map, a day-by-day/stage-by-stage planning view, and a curated list of activities (restaurants, museums, shops, points of interest, hikes). Primarily Android, but also reachable from a browser (desktop, or iOS where there's no native app) via Google OAuth2 — see "Trip database: Google Drive + SAF" below. Built for at most a couple of travelers sharing a trip (not a general multi-user product), but the app manages multiple trips — a trip selector in the header switches between them. Everything about a trip (stages, accommodations, excursions, transport legs, activities) is editable in-app and stored in a single unified JSON file on Google Drive.

## Commands

```bash
npm run dev              # Vite dev server
npm run build             # tsc -b && vite build
npm run lint               # oxlint
npx cap sync android       # copy the web build into the native Android project (run after every build you want to test on device/emulator)
npm run activities:geocode  # resolve lat/lng for activities via Nominatim (rate-limited, resumable — see Pitfalls)
npm run deploy               # web build + cap sync + gradlew assembleDebug + adb install/launch on whatever device is connected (scripts/deploy.ps1) — the one-shot "test this on my phone" command

# Merge data/activities-sources/*.csv into a trip's activities in the shared Drive database
# (release-time bulk import; --trip is optional if the database has exactly one trip):
node scripts/build-activities.mjs --path="G:\Mon Drive\Japplan\database.json" --trip=<tripId>
```

No test suite is configured.

**Android build**: open `android/` in Android Studio and use Run, or `cd android && ./gradlew.bat assembleDebug`. Requires `ANDROID_HOME` set. Gradle's JDK is pinned in `android/gradle.properties` (see Pitfalls) — do not rely on the system `JAVA_HOME`.

## Architecture

### Data model

Single source of truth: a `Database { trips: Trip[] }` (typed in `src/types/trip.ts`), loaded at runtime from a single Drive-backed JSON file by `useDatabase()` (see "Trip database: Google Drive + SAF" below) — nothing trip-related is hardcoded in the repo. `App.tsx` holds the currently-selected `Trip` (via the header's trip selector, persisted across restarts) and passes it down to every view exactly like a plain `Trip` object.

- Each `Trip` is fully self-contained — `id`, `name`, `stages[]`, `departureLegs?`, `activities?` — nested rather than sharing a flat pool with other trips. This was a deliberate choice over a flat `{ stages, activities }` pool with a `tripId` foreign key on each row: it keeps every existing consumer (`MapView`, `Timeline`, `DayView`, `dayPlan.ts`) unaware that multiple trips even exist — they still just receive one `Trip`, same as before multi-trip support existed.
- `Trip.stages: Stage[]` — the itinerary in order. Each `Stage` has `accommodations[]`, `excursions[]` (day trips with their own date/coordinates/transport `mode`), and `arrivalLegs?: TransportLeg[]` describing how you got there from the previous stage (mode + from/to coordinates). `Stage.order` is only ever changed via the ↑/↓ reorder buttons in `Timeline`/`StageCard` (swaps `order` with the adjacent stage) — never exposed as a free-text field, to avoid duplicate/gapped order values.
- `Trip.departureLegs?` — the final leg(s) after the last stage (hotel → airport), since they aren't "arriving" anywhere in-app. Managed from a dedicated "Trajet retour" section at the bottom of `Timeline`, not from a per-stage card.
- `TransportLeg.id` exists purely so `arrivalLegs`/`departureLegs` entries can be individually edited/deleted from the UI — it has no other meaning.
- `Trip.activities?: Activity[]` — a **flat list nested directly under its `Trip`**, not nested under `Stage`. Each activity carries a `stageGroup` (free-text display label, e.g. `"Day-trip town (depuis Main city)"`) and an optional `stageId` linking back to a real `Stage` *within the same trip*. Kept flat and decoupled from `Stage` because day-trip activity groups don't map 1:1 onto a `Stage` in the itinerary.
- `Activity.time?` is an optional `"HH:mm"` start time, in-app-only (like `done`/`rating`/`comment` below, never touched by the CSV upsert) — deliberately distinct from `hours?` (free-text opening hours sourced from the CSV `Horaires` column): `time` is *when you plan to be there*, `hours` is *when the place is open*, and both can be set independently. `time` drives the "par jour" agenda layout (`DayAgenda.tsx`, see below) and by itself has no duration — just a point to position the activity on that day's timeline. `Activity.endTime?` is an optional second `"HH:mm"`, meaningless without `time` (both `TimePickerModal` and `ActivityFormModal` reject an `endTime` set without a `time`, or an `endTime` at or before `time`): when set, the activity becomes a blocked time range on the frise instead of a bare point — see `DayAgenda.tsx` below. Both fields editable via a dedicated `TimePickerModal` (clock icon on `ActivityCard`'s footer, mirroring the calendar icon's `DayPickerModal` for `date`; the chip shows `"09:00–10:30"` once `endTime` is set) or directly in `ActivityFormModal`.
- `Activity.done`/`rating`/`comment` are optional, in-app-only fields (never touched by `build-activities.mjs`'s CSV upsert — it only mutates its own CSV-owned fields on an existing entry, see that script's `existing.*` assignments): `done` marks it as visited, `rating` is a free-form emoji typed via the device's own emoji keyboard (deliberately not a closed set), `comment` is a personal note distinct from the CSV-sourced `notes`. All three are set together in `ActivityRatingModal` (opened from `ActivityCard`'s note/check footer icon) — there's no separate done-toggle — not the general add/edit form (`ActivityFormModal`), so recording them during/after a visit stays a single tap instead of opening the full edit form.
- `Accommodation.coordinates` is optional: only set when a stage has multiple accommodations at genuinely different locations (seen in one stage of the seed data migrated by `scripts/migrate-database.mjs`), so `MapView` knows to draw a second pin.

### App shell (`src/App.tsx`)

Four bottom tabs, each rendered conditionally (not routed): **Carte** (`MapView`), **Planning** (`PlanningView`, which itself toggles between `Timeline` "par étape" and `DayView` "par jour"), **Activités** (`ActivitiesView`), **Ressources** (`ResourcesView`). Switching away from Carte fully unmounts `MapView` — this is relied upon (see below), not accidental.

`App.tsx` calls `useDatabase()` once and gates the whole tab-rendering block on its status being `'ready'` *and* a trip being selected before anything (including the default Carte tab) first mounts. This is deliberate, not defensive boilerplate: `MapView` builds its markers once at mount time (see below), so if `MapView` mounted before the database/selected trip were ready, its very first — and, on a fresh Carte visit, only — marker pass would run against an empty list. `MapView` is also remounted (``key={`${mapOffline}-${resolvedTheme}-${selectedTrip.id}`}``) whenever the selected trip, the offline toggle, or the resolved theme changes, for the same "mounted fresh, built once" reason as the offline-map toggle below — a theme change has to force a fresh mount too, since `MapView` picks its MapLibre style (light/dark) once at mount time (see "Visual design system" below).

All CRUD mutations exposed by `useDatabase()` (activities, stages, accommodations, excursions, transport legs, trips themselves) take a `tripId` as their first argument, since a `Trip` is just one entry in `Database.trips`. `App.tsx` wraps every one of them through a small `withTrip()` helper bound to the currently-selected trip before handing them down to `PlanningView`/`ActivitiesView`/`Timeline` — those components never need to know about `tripId` or which trip is active.

`utils/dayPlan.ts` expands `Stage.accommodations` into one entry per calendar day (`buildDayPlans`), handling multi-accommodation stages, transition days, and the final departure day. Dates are ISO strings parsed as UTC (`` `${iso}T00:00:00Z` ``) everywhere to avoid local-timezone off-by-one bugs.

**Android hardware back button**: none of the app's modals are real navigation — they're plain React state, so there's no web history entry for the native back button to "pop", and by default Capacitor's Android bridge just exits the app the moment it's pressed with an open modal. `src/utils/backButtonStack.ts` keeps a plain module-level stack of `onClose` callbacks; `src/hooks/useBackButtonClose.ts` pushes a callback onto it on mount and pops it on unmount. Every modal in the app is built on `src/components/ui/Sheet.tsx` (see "Visual design system"), which calls this hook itself — individual modal components (`ActivityFormModal`, `SettingsModal`, etc.) never call it directly. `useBackButtonClose` reads `onClose` through a `useRef` rather than putting it in the effect's deps: `Sheet` passes it a `requestClose` closure that's a new reference on every render, and with `onClose` in deps the effect would pop/push the handler on every render — harmless today since no modal is nested inside another, but it would break the LIFO order the moment one is. A single listener in `App.tsx`, registered via `@capacitor/app`'s `App.addListener('backButton', ...)`, closes the top-of-stack modal if one is open, and otherwise calls `CapacitorApp.exitApp()` to preserve the original behavior when nothing is open. `@capacitor/app`'s web implementation never fires `'backButton'` (it's Android-native only, see its `web.js`), so this can only be exercised on-device — same class of limitation as the SAF picker below.

**Safe areas / edge-to-edge (status bar, gesture nav)**: Capacitor 8 auto-registers a `SystemBars` plugin (part of `@capacitor/core`, not a separate package to install) that injects `--safe-area-inset-{top,right,bottom,left}` onto `document.documentElement` and handles the edge-to-edge layout `targetSdk 36` forces on Android — no `@capacitor/status-bar` needed. This only works with `viewport-fit=cover` in `index.html`'s viewport meta (present) **and** a WebView recent enough to support the passthrough mode; on an older WebView, `SystemBars` pads the native view instead and the injected insets read `0`, which is why every safe-area consumer in the CSS uses the double-fallback form `var(--safe-area-inset-bottom, env(safe-area-inset-bottom, 0px))` (aliased to `--sai-bottom`/`--sai-top` in `src/index.css`) rather than bare `env(...)` — `env()` alone is only correct in the passthrough mode. `.app__header` and `.tab-bar` are the only two places that actually need the inset (they sit at the physical top/bottom edge); nothing *inside* `.app__content` should add its own safe-area padding on top of that, since the tab bar already reserves the space above the gesture-nav area — an early version of the FAB double-counted this and sat too high.

### Visual design system (`src/theme/`, `src/components/ui/`)

The app follows a deliberate "japonisant sobre" visual language (washi-paper surfaces, sumi-ink text, vermillon/indigo/gold accent roles) rather than ad-hoc per-component styling. Three layers:

- **`src/theme/tokens.css`** — the token layer: surfaces, ink/text, hairlines, the accent roles (`--vermillon`, `--indigo`, `--gold`, `--matcha`, `--danger`, `--trail`), spacing/radius/motion scales, and `--font-serif`/`--font-sans`. Declares both a light `:root` block and dark overrides gated two ways — `@media (prefers-color-scheme: dark)` under `:root:not([data-theme='light'])`, and `:root[data-theme='dark']` — so an explicit user choice always wins over the OS. Imported by `src/index.css`, which is otherwise just a reset plus a **compatibility bridge**: the 7 original CSS vars (`--text`, `--bg`, `--accent`, etc.) are redefined as aliases onto the new tokens (`--bg: var(--surface-0)`) so `App.css` didn't need a single flag-day rewrite — most of `App.css` still reads the old names, some of it (screens redone during the redesign) reads the new tokens directly. Both resolve to the same values; don't "fix" the old names by removing the bridge.
- **`src/hooks/useTheme.ts`** + **`src/theme/theme.ts`** — the Auto/Clair/Sombre setting (`SettingsModal`'s "Apparence" section), persisted via `@capacitor/preferences` under key `themePref`, same pattern as `useOfflineMap`/`offlineMapRepository`. `useTheme()` resolves `'auto'` against `matchMedia('(prefers-color-scheme: dark)')`, writes a **concrete** `data-theme="light"|"dark"` onto `<html>` (never `"auto"` — the token-layer CSS above has no rule for that value), and calls `SystemBars.setStyle(...)` from `@capacitor/core` to recolor the status bar icons. That call **must** stay wrapped in `.catch(() => {})`: `@capacitor/core`'s web implementation of `SystemBars` unconditionally throws (it's a native-only plugin), so an unguarded call blows up `npm run dev`.
- **`src/theme/categories.ts`** — the single source of truth for activity-category and transport-mode colors/labels (`categoryLabels`, `CATEGORY_COLORS`, `TRANSPORT_COLORS`, `TRAIL_COLOR`), read by both React components (`Chip`, `MapFilterModal`, form selects) and `MapView.tsx`'s imperative MapLibre code. Colors live here as TS literals — keyed by resolved theme — rather than being read out of CSS custom properties, because MapLibre's `addLayer`/`setPaintProperty` need a literal string synchronously at call time; reading `getComputedStyle` there would be racy and unnecessarily indirect. `writeColorVars(root, theme)` is the one place that *does* project these onto CSS, writing `--cat-{category}`, `--cat-{category}-wash`, and `--transport-{mode}` onto `<html>` — called by `useTheme()` on every resolve, which is what lets `<Chip tone="category">` and `MapView`'s markers (see below) pick up the right color via `var(--cat-restaurant)` etc. without their own theme-change listener. `categoryLabels` used to live in (and be exported from) `ActivityCard.tsx`; it moved here specifically so this file could be the *only* place category color/label pairs are defined.
- **`src/components/ui/`** — five hand-rolled primitives, no external UI/icon library: `Sheet` (the bottom-sheet shell every modal is built on — header, backdrop, footer, safe-area padding, exit animation, owns `useBackButtonClose` itself), `Button` (`variant` × `size`, `iconOnly`, `loading`; defaults to `type="button"` since most call sites live inside `<form>`), `Chip` (filter/status pills — `tone="category"` reads `--cat-{category}`/`-wash` inline, other tones use static `--chip-accent`/`--chip-wash` set by a `chip--tone-*` class), `Icon` (a `Record<IconName, string>` of raw SVG path data rendered inline — `iconHtml(name)` renders the same paths as an HTML string for MapLibre's popup template strings, which can't render React), and `Field` (label + input wrapper matching `Sheet`'s form styling). Prefer these over new ad-hoc markup/CSS for any new UI — the whole point of extracting them was to stop each modal/screen from re-inventing its own button/chip/field look.

Fonts (`src/theme/fonts.css`, files in `src/assets/fonts/`) are **embedded locally as `.woff2`**, not loaded from Google Fonts at runtime — the app needs to render correctly on a trip with no connectivity. Noto Serif (titles, `h1`/`h2`, card group headers) + Inter (everything else), each split into `latin`/`latin-ext` subsets via `unicode-range` so a purely-French UI only ever downloads the `latin` file. The four `.woff2` files are **variable fonts**, not per-weight static files: Google's `css2` API, when asked for specific weights of a family that's actually variable, serves the same underlying file for multiple `font-weight` values (confirmed by inspecting the raw response — `Inter` weight 400/500/600 all point at one URL) rather than three separate files, which is why there are 4 files here covering a `400 600` weight range each rather than 10+. If more weights are ever needed, they very likely don't require new files — just widening the `font-weight` range in the existing `@font-face` rules.

### Timeline / StageCard (`src/components/Timeline.tsx`, `StageCard.tsx`)

The "par étape" Planning view renders stages on a vertical **spine**: `<ol className="spine">` in `Timeline.tsx`, each stage a `<li className="spine__item">` on a two-column grid (a 28px rail column + content), with a `::before` on `.spine__rail` drawing the connecting line and a numbered `.spine__node` circle in place of what used to be a badge on the card itself (`StageCard` no longer renders any order number — the spine node *is* the number). A stage's `arrivalLegs` are rendered as their own slim `.spine__item--leg` connector rows *between* the two stage nodes they connect, colored via `--node-color` set inline to `var(--transport-{mode})` — not inside `StageCard` at all. `StageCard` only keeps the "+ Trajet d'arrivée" button (opens the same `TransportLegFormModal`, `mode: 'create'`); editing/deleting an existing leg happens from its spine row, which is why `StageCard`'s props have no `onEditArrivalLeg`/`onDeleteArrivalLeg` — only `Timeline.tsx` needs those. `DayView`'s "par jour" list is a flat `.day-view` column of `DayCard`s (no spine across days — a rail spanning ~14 items would be noisy), sharing only the day-card visual language (a 3px left rail colored by what kind of day it is: gold if today, vermillon if a stage transition, indigo if an excursion day). *Within* a single day, though, activities that have a `time` (see the data-model note above) get their own mini vertical spine — `DayAgenda.tsx` — positioned proportionally to their hour rather than sequentially like `Timeline`'s. Each `DayCard` computes its own hour range from its own activities (`[min(time) - 1h, max(time) + 1h]`, floored at a 2h minimum span) instead of sharing a fixed axis across the whole trip: a packed day gets a tall frise, a light day a short one, and a day with no timed activities renders no frise at all — just the flat "Non planifiées" list, unchanged from before this feature. Two activities scheduled close together (or, for the anti-collision math, *any* two activities regardless of `endTime`) would otherwise visually overlap; `DayAgenda` resolves this by bumping a colliding entry down just far enough to clear the previous one (never earlier than its own proportional slot) rather than trying to model real overlap — this bump is based purely on `time`, deliberately not on `endTime`/duration, to keep the collision math simple for what's still fundamentally a personal single-user planner. `endTime` instead feeds a second, independent visual: a colored segment thickening `DayAgenda`'s rail (`.day-agenda__span`) from the activity's true (un-bumped) start position to its true end position, sized by actual duration — deliberately *not* a filled/shaded block behind the card, because the card's own fixed height (see `ENTRY_HEIGHT` below) often exceeds a short activity's duration and would fully hide a duration block sized to fit behind it; a colored rail segment stays visible regardless of how the card itself got sized or bumped. An activity without `endTime` gets no segment, just its usual dot. Activities inside the frise render as `ActivityCard`s in `compact` mode (hides `hours`/`notes`/`comment`, the "En Maps" link, and the wishlist flag — kept lean since the point of the frise is a chronological scan, not the full card detail available elsewhere) — sized to fit the entry height the collision math assumes (`ENTRY_HEIGHT` in `DayAgenda.tsx`, kept in sync with `.day-agenda__entry`'s CSS `min-height` the same way other coupled constants in this codebase are commented).

### MapView (`src/components/MapView.tsx`)

MapLibre GL is driven **imperatively** inside a single mount-once `useEffect`, not through React state/props — markers, popups, and layers are created with the raw MapLibre API. This is deliberate: since the Carte tab fully unmounts on tab switch, the map is recreated from scratch every time it's shown anyway, so there's no benefit to reactive re-rendering. The `selectedStageId` prop (used for "fly to this stage" when tapping a stage elsewhere in the app) is read **once** inside the `'load'` handler at mount time for the same reason — it intentionally does not react to prop changes after mount.

Transport route lines are colored/dashed per `TransportMode` (`routeLineStyle(mode, theme)` — a function, not a static object, since colors come from `src/theme/categories.ts`'s `TRANSPORT_COLORS` and differ by resolved theme). Ground modes (shinkansen/train/bus) are routed through the public OSRM driving API as a *visual approximation* of the real route (not actual rail lines), falling back to a straight line on failure. Plane/ferry legs are always straight lines.

Long-press-to-reveal-address is implemented with manual `touchstart`/`touchmove`/`touchend` timers, not the browser's native `contextmenu` event — MapLibre's own touch gesture handling prevents `contextmenu` from firing reliably on mobile (see Pitfalls).

Activity markers are colored by category via a `--marker-color` CSS custom property set inline (``el.style.setProperty('--marker-color', `var(--cat-${category})`)``) rather than a per-category class — one `.activity-marker` CSS rule instead of one per category, and markers recolor themselves automatically when the theme changes (no marker-rebuild code needed) since `--cat-*` lives on `<html>`, written by `writeColorVars()` (see "Visual design system"). A toggle UI hides categories on demand (all 6 categories start active/visible). Only activities with resolved `coordinates` get a marker.

`MAP_STYLES` picks an OpenFreeMap style keyed by resolved theme (`bright` for light; OpenFreeMap has no dark style, so `positron` — its least-aggressive desaturated option — stands in for dark online). Offline, `buildOfflineStyle(theme)` calls `namedFlavor(theme)` from `@protomaps/basemaps`, which *does* have a real `dark` flavor, plus a theme-matched sprite URL (`.../sprites/v4/${theme}`) — so the online/offline dark experience is asymmetric by necessity, not oversight.

### Trip database: Google Drive + SAF

Nothing trip-related is bundled in the app. The single source of truth is one unified JSON file (`Database { trips: Trip[] }`) living on Google Drive, at `G:\Mon Drive\Japplan\database.json` on the dev PC (Google Drive Desktop mounts it there — read/write it like any local file, no API). Three completely decoupled ways of reaching the *same* cloud file:

- **On the PC (releases)**: normal file I/O on the `G:\...` path — that's it.
- **In the app (Android)**: via the Storage Access Framework. `android/app/src/main/java/com/pdcaux/japplan/DriveFilePlugin.kt` (a custom Capacitor plugin — `DriveFile` — the repo's only Kotlin code) exposes `pickFile()` (native `ACTION_OPEN_DOCUMENT`, Google Drive's Android app shows up as a picker source since it registers a `DocumentsProvider`), `hasPersistedAccess()`, `readText()`, `writeText()`. `pickFile()` calls `takePersistableUriPermission()` so the chosen `content://` URI keeps working across app restarts — the URI + display name are cached via `@capacitor/preferences` so the picker only needs to run once. `src/plugins/DriveFile.ts`/`.web.ts` wrap it.
- **In a browser (web build)**: via Google OAuth2 + the Drive REST API — this is what lets someone on desktop Chrome/Firefox or on iOS (which has no native app) reach the same file. `src/services/googleAuth.ts` wraps Google Identity Services' (GIS) OAuth2 token client (`https://www.googleapis.com/auth/drive.file` scope — deliberately the narrow, non-sensitive scope that only grants access to files the user explicitly picks via the Google Picker, never the whole Drive; this is also what makes it safe to publish the OAuth consent screen to "In production" unverified, since an uninvited visitor who reaches the consent screen still can't select any file that hasn't been Drive-shared with their account). `src/services/googlePicker.ts` wraps the Google Picker (`gapi.load('picker', ...)`, two `DocsView`s — "My Drive" and, via `.setOwnedByMe(false)`, "Shared with me", since the second user's copy lives there). `src/plugins/DriveFile.web.ts` implements `pickFile()`/`hasPersistedAccess()`/`readText()`/`writeText()` on top of these two services and the Drive REST API (`GET .../files/{fileId}?alt=media`, `PATCH .../upload/files/{fileId}?uploadType=media`) — `databaseRepository.ts`/`useDatabase.ts` need zero changes, since `uri` is just as opaque a string (a Drive `fileId`) to them as the Android `content://` URI was. `readRange`/`closeRangeRead` (used only by the offline map, see below) stay unimplemented on web — `offlineMapRepository.connectMapFile()` explicitly refuses to even open the picker on web (`Capacitor.isNativePlatform()` check) rather than let someone "connect" a map file it can then never actually read.

GIS has no durable refresh token for a pure client-side app: `getAccessToken()` caches the access token in memory (~1h lifetime) and, for background checks (`interactive: false`, e.g. `hasPersistedAccess`), retries a silent renewal (`prompt: ''`) that fails cleanly (mapped to the existing `AccessRevokedError`/"reconnect" UI) if the browser session can't resolve it invisibly. For the explicit "Choisir le fichier Google Drive" click (`interactive: true`), it deliberately does *not* try silent-then-interactive as two sequential calls — see the popup-blocking pitfall below.

`src/data/databaseRepository.ts` (load/save/connect, typed errors) + `src/hooks/useDatabase.ts` (the `'loading' | 'no-file' | 'error' | 'ready'` state machine, full CRUD for trips/stages/accommodations/excursions/transport legs/activities, each mutation writing the *entire* `Database` back in one shot with optimistic update + rollback-on-write-failure) are the only things that touch the plugin. The desktop path (`G:\Mon Drive\...`) and the Android `content://` URI never need to match — Google Drive's own sync is what unifies the file's identity, not a shared path. This replaced an earlier `activitiesRepository.ts`/`useActivities.ts` pair (flat `Activity[]` file, no trips/stages) — `useDatabase()` uses its own `@capacitor/preferences` keys (`databaseFileUri`/`databaseFileName`) rather than reusing the old ones, so upgrading requires reconnecting the file once from `SettingsModal` (deliberate: the old file's shape doesn't match `Database` and shouldn't be silently reinterpreted).

The currently-selected trip id is persisted separately (`@capacitor/preferences` key `selectedTripId`), read/written by `useDatabase()`'s `selectTrip()`. If the stored id doesn't match any trip in the loaded database (deleted trip, fresh file), it falls back to `trips[0]`.

**Schema migrations**: `Database.schemaVersion` + `src/data/migrations.ts` (`CURRENT_SCHEMA_VERSION`, an ordered `migrations[]` array of `{ toVersion, migrate(db) }` steps, `migrateDatabase()`) exist so a *breaking* change to `src/types/trip.ts` (a field renamed, a field's type/shape changed — not a new optional field, which needs nothing since it's simply absent/`undefined` on old data) doesn't leave an out-of-date Drive file silently misread. `databaseRepository.ts`'s `loadDatabase()` runs `migrateDatabase()` on every load and, if it changed anything, fires a best-effort `saveDatabase()` right after (not awaited, not surfaced as an error — `migrateDatabase()` is idempotent, so a failed write here just gets retried on the next load or the next in-app edit). A file with no `schemaVersion` at all (never migrated) is treated as already being at `CURRENT_SCHEMA_VERSION`, not version 0 — so migrations added *after* a given database already existed don't get replayed against it retroactively; only migrations added after this mechanism itself existed apply. When making a breaking change: bump `CURRENT_SCHEMA_VERSION` and add the matching migration step *in the same change* — the type change and the data transform must ship together, since nothing else in the app converts old shapes to new ones. This does not solve two people's phones running different app versions against the same file at once (the older app still won't understand a renamed field until it updates) — with only one or two travelers sharing a trip, that's accepted as a "update both before a breaking change goes out" manual step rather than something worth engineering around.

The file-connect UI itself (picker button + connected filename + status/error text) lives in `SettingsModal.tsx`, opened via the ⚙ icon in `App.tsx`'s header — not in `ActivitiesView`/`Timeline`, to keep those tabs focused on their own content. When `databaseStatus` is `'no-file'`/`'error'`, or when it's `'ready'` but the database has zero trips, the header's trip selector is replaced by a short inline message pointing at ⚙ (no file) or at "➕ Nouveau voyage…" (empty database) instead of showing a broken/empty `<select>`.

**Release-time bulk import** still starts from CSV, same as before: `data/activities-sources/*.csv` (one file per region, columns `Nom,Étape,Type,Lien Google Maps,Horaires,Notes`) →

1. `scripts/geocode-activities.mjs` — resolves lat/lng via Nominatim into `data/activities-coordinates.json`, keyed by Google Maps `place_id`. Only geocodes cache misses, safe to re-run.
2. `node scripts/build-activities.mjs --path="G:\Mon Drive\Japplan\database.json" --trip=<tripId>` — parses all CSVs (dedup by `place_id`, `STAGE_ID_BY_GROUP` for `Étape` → `Stage.id`, extend that table for new regions), then **upserts into the target trip's `activities[]` by `place_id`**: a match overwrites that entry's CSV-owned fields in place (keeping its `id`; coordinates only overwritten when the cache actually has a value, never blanked on a cache miss); no match appends a new entry. Entries never seen in any CSV — i.e. added directly in the app — are left completely untouched. `--trip` can be omitted only while the database has exactly one trip. This is what lets releases keep enriching the base without clobbering what was added on-device.

`scripts/migrate-database.mjs` is the one-off script used to move off the old hardcoded-`trip.ts` + flat-`activities.json` setup onto the unified `Database` file (`--source=<old activities.json> --out=<new database.json>`) — it duplicates the stages/departureLegs that used to live in `src/data/trip.ts` (now deleted) as literal data, same "duplicate on purpose" reasoning as the older CSV migration script below. Only needed again if the Drive file is ever lost/recreated from scratch. **Always run it against a local copy of the source file first** (e.g. copied into a scratch/temp directory, never the real Drive file), reconnect the app to that local copy, and validate the full CRUD flow end-to-end before ever pointing `--out` at the real Drive path — there is no automatic safety net against overwriting real data.

`scripts/migrate-activities-to-json.mjs` is the older one-off script that originally seeded the flat Drive activities file from the CSVs, predating trips/stages being in the database at all (same parsing logic, duplicated on purpose — see its header comment). Kept for historical reference; `migrate-database.mjs` is what actually matters now.

The "Itinéraire" link in popups/cards always uses the activity's **original** Google Maps URL (with its `place_id`), not a link built from the Nominatim-geocoded coordinates — the geocoded coordinates are only for placing the pin on our own map, Nominatim's result is sometimes less precise than Google's.

When Nominatim can't find a place (small/obscure venues are common misses — see Pitfalls), the fallback is manual: resolve `https://www.google.com/maps/place/?q=place_id:<ID>` in a real browser tab and read the resulting `@lat,lng` from `location.href` after Maps' client-side JS rewrites the URL (add a short delay — the rewrite isn't synchronous with page load). A plain `fetch()` of that URL does **not** work: it returns a generic map-preview fragment centered on an unrelated default location, not the resolved place — this was tried and confirmed non-viable, don't retry it. There is no batch/API shortcut for this fallback; each miss needs its own real navigation. All 232 current activities are geocoded; this fallback only matters again when a new CSV introduces fresh misses.

### Carte hors ligne (`src/hooks/useOfflineMap.ts`, `src/components/SettingsModal.tsx`)

`SettingsModal` is the single ⚙ modal for both Drive-backed connections in the app: the trip database section (state from `useDatabase`) and this offline-map section (state from `useOfflineMap`), each independent and rendered as its own section — there's no shared "settings" state between them beyond living in the same modal.

Same Drive + SAF architecture as the trip database, applied to map tiles: a **PMTiles** archive (single-file vector tile format, readable by byte-range without a server) lives at `G:\Mon Drive\Japplan\japan.pmtiles` on the dev PC — currently ~1.6 GB, zoom 0–14, covering the main Japanese islands (bbox `122.5,24.0,146.5,45.7`; see the `extract` command below to regenerate it). A smaller test extract, `tokyo-test.pmtiles` (~24 MB, central Tokyo only), is also kept on the same Drive folder for quick on-device iteration without waiting on the full file. The user connects one of them via the same `DriveFile.pickFile()` picker used for `database.json` (a second, independent URI persisted under different `@capacitor/preferences` keys — see `src/data/offlineMapRepository.ts`). Unlike `database.json`, **there is no local copy**: `DriveFilePlugin.readRange({ uri, offset, length })` reads byte ranges straight from the Drive `content://` URI on demand (keeping one `ParcelFileDescriptor` open per URI across calls — reopening one per tile read would make panning laggy). `src/utils/offlinePmtilesSource.ts` implements the `pmtiles` package's `Source` interface on top of `readRange`, registered globally via `pmtiles.Protocol`/`maplibregl.addProtocol('pmtiles', ...)` once at module load in `MapView.tsx` (same pattern as its existing `setWorkerUrl()` call) — the actual `PMTiles` instance for the connected file is (re)added to the protocol at mount time.

`MapView` picks between the remote OpenFreeMap style (`MAP_STYLES[theme]`) and an offline style built at mount time from **`@protomaps/basemaps`** (`buildOfflineStyle(theme)`, calling `layers(sourceName, namedFlavor(theme))`), based on `offline`/`theme` props read once at mount like everything else in this component. **This is not the same cartographic style as online** — it can't be, and reusing OpenFreeMap's Bright style JSON offline was tried first and silently rendered almost nothing (see pitfall below): the offline PMTiles archive is extracted from Protomaps' own basemap (`data.source.coop/protomaps/openstreetmap`), which uses Protomaps' own vector layer schema, not OpenMapTiles (what OpenFreeMap/Bright is built for) — the two schemas share no layer names. `@protomaps/basemaps`' `layers()` generates a full layer array already matched to that schema. `App.tsx` forces a clean remount on toggle (trip change, or theme change) via ``<MapView key={`${mapOffline}-${resolvedTheme}-${selectedTrip.id}`}>`` rather than teaching `MapView` to react to the props — consistent with the "mounted fresh every time" philosophy already documented above. The offline style's `sprite`/`glyphs` point at Protomaps' own asset CDN (`protomaps.github.io/basemaps-assets`), not bundled/cached — offline label text/icons are best-effort only, degrading gracefully to an unlabeled basemap if never cached by prior online use.

**Generating/updating the PMTiles archive** (release-time, done on the PC, no in-app "download" mechanism by design — see pitfall below): the `pmtiles` Go CLI (`protomaps/go-pmtiles` releases on GitHub — no npm package, download the platform binary directly from GitHub releases) can `extract` a bbox directly from Protomaps' public daily-built planet basemap over HTTP range requests, without downloading the full (100+ GB) source:

```bash
pmtiles.exe extract https://data.source.coop/protomaps/openstreetmap/v4.pmtiles japan.pmtiles --bbox=122.5,24.0,146.5,45.7 --maxzoom=14
```

That bbox (west,south,east,north) is what `japan.pmtiles` was actually generated with — reuse it as-is for updates so the coverage doesn't silently shrink/grow between releases; only widen it deliberately (e.g. to include Okinawa's outer islands) and note the change here. Extraction only transfers the chunks it needs (~1.8 GB transferred for this 1.6 GB archive, not the full 100+ GB source) but still takes a minute or two — run it in the background rather than blocking on it. Drop the result at `G:\Mon Drive\Japplan\japan.pmtiles` (same filename each time — the phone's persisted `content://` URI stays valid across updates, no reconnection needed, exactly like `database.json`). Sanity-check a fresh extract before shipping it by reading its header/a sample tile with the `pmtiles` npm package and a small Node script (`new PMTiles(customFsSource).getHeader()` / `.getZxy(z,x,y)`) — cheaper than a full on-device round-trip to catch a bad bbox or empty archive.

### ActivitiesView (`src/components/ActivitiesView.tsx`)

Filtering is entirely client-side and recomputed in one `useMemo`: category chips (multi-select, empty selection = no filter = show all) combine with a free-text search box that matches against both `name` and `notes`, diacritic-insensitive (`normalize()` strips combining marks via `NFD` + regex — the same trick used for CSV slug generation in `build-activities.mjs`, kept separate rather than shared since one runs in Node and the other in the browser). The running total and each section's `(count)` are derived from the same filtered list, not tracked separately, so they can't drift out of sync with what's actually rendered.

`ActivityCard`'s footer actions are icon-only buttons/chips: a flag toggles `wishlist` directly via `onToggleWishlist` (no confirmation), a calendar icon opens `DayPickerModal` to set `date` (becomes a filled chip showing the date once set), a clock icon opens `TimePickerModal` to set `time` (same filled-chip-once-set pattern, showing `"HH:mm"`), and a note/check icon opens `ActivityRatingModal` — a small dedicated form for `done`/`rating`/`comment` only (`done` is set *inside* that modal, there's no separate done-toggle button) — kept apart from `ActivityFormModal` (see the data-model note above). All of these are also wired up in `DayCard`/`DayView` (the Planning "par jour" view), not just here, so an activity can be marked done/rated/wishlisted/timed from either place. `categoryLabels`, `CATEGORY_COLORS`, and `TRANSPORT_COLORS` live in `src/theme/categories.ts`, not in `ActivityCard.tsx` — see "Visual design system" below for why.

## Conventions

- Always respond to the user in French.
- Marker/popup HTML for MapLibre is built as raw template strings, not JSX — `Marker`/`Popup` content is plain DOM, not a React tree.
- UI copy is in French throughout (personal app for a French-speaking user).
- No comments except to explain non-obvious *why* (a constraint, a workaround, an invariant) — see existing files for the level expected.
- New UI reaches for `src/theme/tokens.css` custom properties and the `src/components/ui/` primitives (`Sheet`, `Button`, `Chip`, `Icon`, `Field`) first — no new raw hex colors, no new hand-rolled modal/button/chip markup, no new emoji used as a UI icon. The only emoji left in the app are user *data* (`Activity.rating`, `Resource.icon`) — those stay emoji on purpose (free-form, typed via the device's own emoji keyboard), never route icon-affordance emoji (✏🗑📅 etc.) back in.
- **Commit messages and PR titles/descriptions**: Conventional Commits format, with French text after the prefix — `<type>: <description en français>` (e.g. `fix: corrige le plantage sur fichier de base de données vide`, `feat: ajoute le tri par date dans Activités`). Common types: `feat`, `fix`, `refactor`, `chore`, `docs`, `style`, `test`. A PR description's body (summary bullets, test plan) is also in French; only the Conventional Commits type prefix itself and standard boilerplate (e.g. the `Co-Authored-By` trailer) stay in English.

## Known pitfalls

- **MapLibre GL + Vite dev-mode dependency pre-bundling breaks its Web Worker auto-detection** — tiles silently never load, no console error. Fixed via `setWorkerUrl()` pointed at `maplibre-gl/dist/maplibre-gl-csp-worker?url` in `MapView.tsx`. Do not "fix" this by excluding `maplibre-gl` from Vite's `optimizeDeps` — that breaks its CJS/ESM default export instead and is a worse failure mode.
- **Vite is pinned to 6.x**, downgraded from the 8.x/rolldown-vite default that `npm create vite` currently scaffolds. If bumping Vite, retest that the map still renders in dev.
- **Android Gradle build runs on whatever JDK Android Studio's bundled JBR currently is**, not the system `JAVA_HOME` — `android/gradle.properties` pins `org.gradle.java.home` to that JBR path; don't remove that line without checking the JDK/Gradle/AGP compatibility matrix. Android Studio auto-updated its JBR to JDK 25 at one point, which broke the build two different ways until fixed (2026-09): (1) Gradle itself refused to run on JDK 25 ("Unsupported class file major version 69") until bumped to **Gradle 9.1.0** (`android/gradle/wrapper/gradle-wrapper.properties`) — the first Gradle release supporting a JDK 25 daemon; AGP stayed at `8.13.0`, no AGP bump needed. (2) Kotlin `2.0.21` (see below) can't target JDK 25 either and silently falls back to targeting 22, which then conflicts with the Java 21 target Capacitor's generated `app/capacitor.build.gradle` sets, failing with "Inconsistent JVM-target compatibility". Fixed by pinning `kotlinOptions { jvmTarget = "21" }` explicitly in `android/app/build.gradle`'s `android {}` block, matching Capacitor's Java target — do this instead of trying to install/target a matching JDK, since bytecode target is independent of the host JDK Gradle runs on. If the JBR jumps version again, re-check both fixes still apply. `scripts/deploy.ps1` exercises this whole path end to end.
- **Corporate/antivirus SSL inspection** (e.g. Norton's web shield) can break `gradlew`'s self-download of the Gradle distribution with a generic certificate error, unrelated to the JDK issue above.
- **Nominatim rate-limits aggressively** (HTTP 429) under bursty/automated use. `geocode-activities.mjs` detects 429 and backs off/retries — don't lower its delay or run it concurrently with other Nominatim traffic, and don't treat a non-429 empty result as equivalent to a 429 (the script already distinguishes these; a naive `!res.ok` check does not).
- **Two Google Maps link formats carry the `place_id` differently**: real "share" links from the Google Maps app use `...&query_place_id=XXX`, but links reconstructed by hand or by another tool directly from a known place_id use `?q=place_id:XXX` instead (this is the same format used by the manual-fallback URL documented above). `placeIdOf()` in all three scripts (`geocode-activities.mjs`, `build-activities.mjs`, `migrate-activities-to-json.mjs`) tries both patterns — if a CSV's rows are silently skipped (row count doesn't budge, "0 à géocoder" despite new rows), check which format that CSV's `Lien Google Maps` column actually uses before assuming something else is broken. **The `?q=place_id:XXX` format must never end up as a CSV's stored `mapsUrl`**: it resolves fine when opened in a JS-executing browser tab (that's why it's safe for the manual geocoding fallback), but the Google Maps *Android app* intercepts it via its own deep-link handling and treats it as a literal text search instead of resolving the place_id, showing "place not found" for many entries. Every `Lien Google Maps` column must use the official cross-platform format instead: `https://www.google.com/maps/search/?api=1&query=<name>&query_place_id=<ID>` (this is what real Maps "share" links already produce, and what one region's CSV was retroactively rewritten to after this broke the "Itinéraire" button for ~65 activities on-device).
- Some activity CSV `Nom` fields include a descriptive suffix (e.g. `"Byōdō-in + musée Hōshōkan"`, `"Honke Daiichi-Asahi (ramen)"`) that breaks Nominatim search; the geocode script retries with the name truncated at the first `" ("` or `" + "`.
- A browser tab left in a backgrounded (`document.hidden`) state throttles `requestAnimationFrame`, so MapLibre's canvas never fires `'load'` even though data/network are fine — don't conclude the map is broken from a headless/backgrounded preview tool alone; verify in a real, focused browser or on-device.
- **Kotlin Gradle plugin version is pinned to `2.0.21`** (`android/build.gradle` buildscript classpath, kept in sync manually with `kotlinVersion` in `android/variables.gradle` — `buildscript{}` must stay the very first block in `android/build.gradle`, so it can't read `variables.gradle`'s `ext` property and the version is hardcoded there instead). Confirmed working against the pinned AGP `8.13.0`/`compileSdk 36`. If bumping AGP, re-verify `compileDebugKotlin` still succeeds.
- **Google Drive's `DocumentsProvider` does not reliably honor SAF's `"wt"` truncate mode**: `openOutputStream(uri, "wt")` was observed leaving trailing bytes from a previous, longer write appended after a shorter new write, silently corrupting the JSON file (a `writeText()` call that should have produced valid JSON left ~25 stray bytes from the prior write tacked onto the end — first observed on the old flat `activities.json`, same risk applies to `database.json`). Fixed in `DriveFilePlugin.kt`'s `writeText()` by opening with `openFileDescriptor(uri, "rwt")` and explicitly calling `FileOutputStream(fd).channel.truncate(bytes.size.toLong())` after writing — don't revert to a plain `openOutputStream(..., "wt")` call, the mode flag alone is not sufficient on this provider. If the Drive JSON ever fails to parse again, this is the first thing to suspect; check the tail of the file for leftover bytes from a shorter prior version before assuming the data itself is wrong.
- The SAF/Google Drive file picker (`DriveFilePlugin.kt`) **cannot be exercised in this environment's headless/backgrounded preview browser** — same category of limitation as the MapLibre `document.hidden` pitfall above, but stronger: the native plugin literally doesn't exist outside the Android runtime (`DriveFile.web.ts` only rejects). Verify on a real device: install the debug APK, use the picker, force-close and relaunch to confirm the persisted permission survives a cold start (the actual point of `takePersistableUriPermission`), then confirm an in-app add/edit/delete lands in the Drive file from the desktop side.
- **The offline map only works truly offline if the connected PMTiles file is marked "Disponible hors connexion" in the Google Drive app itself.** Connecting it via our SAF picker (`DriveFile.pickFile()`) only grants *access* to the `content://` URI — it does not make Drive cache the file's bytes locally, and marking it offline isn't instant either (Drive still needs a live connection to actually download the full file before the mark takes effect). Confirmed on-device: without a fully-cached file, `readRange()`'s `openFileDescriptor()` throws `FileNotFoundException: ... Cello error 2` (Cello being Drive's internal sync engine) the moment there's genuinely no network — even though the app shows the file as "connecté". Not something our code can detect or trigger (SAF has no API for it) — `SettingsModal` surfaces this as a persistent on-screen reminder rather than a one-time toast, since it's easy to forget before a trip. With `japan.pmtiles` at ~1.6 GB, that initial Drive download is not instant even on good wifi — do it days ahead of departure, not the night before. If this error resurfaces, first check the file's offline-availability status in the Drive app itself before assuming a code regression.
- **`PluginCall.getLong(key)` returns `null` for a JS `0`, not `0L`** — Capacitor/org.json stores small whole numbers from the JS bridge as `Integer`, and `getLong()` doesn't coerce, so `call.getLong("offset") ?: reject(...)` was incorrectly rejecting every read starting at offset 0 (i.e. every very first tile). Fixed in `readRange()` by using `call.getDouble("offset")?.toLong()` instead, which reliably handles any JS number including 0. Prefer `getDouble()` over `getLong()` for any future numeric plugin parameter that JS might legitimately send as 0.
- **MapLibre fires a silent `'error'` event on a failed source/tile/style fetch — it never throws and never logs anything on its own.** A broken style or protocol (e.g. the offline pmtiles wiring while it was being debugged) just renders a blank map with zero trace, unless something is listening. `MapView.tsx` registers `map.on('error', (e) => console.error(...))` specifically so this isn't silent again — don't remove it, and check this listener's output first (via `adb logcat --pid=<pid>`, filtering for `Capacitor/Console`) when the map renders blank instead of assuming the cause without evidence.
- **A CSS or JS block comment containing the literal two-character sequence `*/` closes early**, silently, wherever it appears — not just at the intended end. Writing a comment like `/* ... --cat-*/--transport-* ... */` (documenting a wildcard class-name pattern) closes the comment at the embedded `*/` and dumps the rest as live code, producing confusing cascades of parser errors far from the real mistake (seen both in a `.css` file, where PostCSS reported an "Unknown word" several lines later, and in a `.ts` file, where `tsc` reported dozens of unrelated-looking syntax errors). When documenting a glob/wildcard-ish pattern inside a comment, write it as `--cat-* and --transport-*` (or otherwise avoid a bare `*/`), not `--cat-*/--transport-*`.
- **Vite's dev server can serve stale, since-fixed errors from its own module graph** after several rapid sequential edits to interdependent files (e.g. removing a named export from one file while several importers are mid-edit) — the browser console shows `does not provide an export named 'x'` or a stale babel parse error pointing at code that, on disk, is already correct and passes `tsc -b`/`vite build` cleanly. Don't trust a dev-server error over a passing typecheck/build without first hard-reloading; if it persists, stop the preview server, delete `node_modules/.vite`, and restart it — the module graph rebuilds clean. Also worth checking `read_console_messages` history isn't just replaying old messages across a navigation — a genuinely fresh tab/reload is the reliable way to tell a live error from a stale one.
- **`adb shell input tap` is not reliable for on-device verification on this project's test phone (Samsung, One UI)**: taps can register with several seconds of lag (so a second tap queued shortly after can land on whatever the *first*, delayed tap produced), and taps near the left screen edge risk triggering a Samsung Edge-panel gesture that switches to an unrelated app entirely — both were observed causing a tap meant for one button to land somewhere else in the app (once nearly confirming a destructive delete dialog). When verifying UI on-device via adb: prefer generous waits (1–2s) between a tap and its follow-up screenshot, avoid tapping close to the physical left/right edges, and screenshot-before-tapping when unsure of current state rather than chaining blind taps. For anything destructive-adjacent (delete confirmations), read the screenshot before assuming a tap landed where intended.
- **Google Identity Services (GIS) opens a real popup window for every `requestAccessToken()` call — including the "silent" `prompt: ''` renewal, not just interactive consent.** It is *not* a hidden iframe. Combined with lazily loading the GIS script only on first use, the async script-fetch happening mid-click pushed the popup call far enough from the original click event that browsers' popup blockers rejected it (`[GSI_LOGGER]: Failed to open popup window ... Maybe blocked by the browser?`), even in a normal desktop browser, not just this environment's automated preview (which blocks popups unconditionally regardless — expect that failure mode there always, and verify the real flow in an actual browser tab instead). Fixed in `googleAuth.ts` by loading the GIS script eagerly at module import time (so it's ready long before any click) and, for `interactive: true` (the explicit "Choisir le fichier" click), making a *single* `requestAccessToken()` call with no forced prompt rather than chaining a silent attempt first — a second sequential popup call after the first one's async callback is one hop too many from the original gesture and gets blocked too.
- **Google Picker requires a Cloud project *number* (`setAppId`), not just the API key (`setDeveloperKey`), specifically because of the `drive.file` scope** — omitting it doesn't error at config time, it fails at runtime as `"The API developer key is invalid"` even with a perfectly valid key. Set via `VITE_GOOGLE_PROJECT_NUMBER` (`googlePicker.ts`) — find it on the Cloud project's dashboard, distinct from (and easy to confuse with) the project *ID*.
- **The Picker API key's HTTP referrer restriction must include `https://docs.google.com/*`, not just the app's own origin.** The Picker UI itself renders inside an iframe hosted on `docs.google.com`, so *that's* the origin Google checks the key's referrer restriction against for part of the flow — an app-origin-only restriction also produces `"The API developer key is invalid"`, indistinguishable from the missing-`setAppId` case above without checking both. Same for the key's API restrictions: it needs both **Google Picker API** and **Google Drive API** selected, not Picker alone.
- **The OAuth Client's "Authorized JavaScript origins" must exactly match the origin actually making the request, including the port** — a dev server that happens to start on a fallback port (e.g. because something else, like an agent's own preview tooling, already holds 5173) silently produces `Erreur 401: invalid_client — no registered origin` with no indication the port is the culprit. Always confirm the actual port in the browser's address bar before assuming the Cloud Console config is wrong.
- **A fresh "Testing"-status OAuth consent screen caps refresh tokens at 7 days**, independent of the `drive.file` scope choice — switching Publishing status to "In production" (still unverified, still showing the "Google hasn't verified this app" click-through) removes that cap without needing Google's verification review, which would be overkill for a 2-person personal app. Verified against current (2026) Google Cloud Console docs; the old "OAuth consent screen" single-page UI is now "Google Auth Platform" with Branding/Audience/Clients tabs — the publishing-status toggle lives under Audience.
- Do not run `git commit` unless explicitly asked for that specific change, even after committing earlier in the same session — ask first each time.
